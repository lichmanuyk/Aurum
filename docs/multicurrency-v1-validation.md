## Денежная модель

- Валюта счёта определяет единицы операций и остатка. Валюта актива определяет единицы оценок. После появления истории менять единицы нельзя.
- Перевод хранит списанную и фактически зачисленную суммы. Для одинаковых валют они совпадают; комиссию записывают отдельно. Recurring cross-currency posting требует фактическую сумму зачисления.
- Goal, Budget и порог неактивных денег имеют фиксированные валюты. Смена валюты отчётов их не меняет.
- Расчёты сервера используют Decimal, округление HALF_EVEN и точность валюты; JPY/KRW без дробной части. Остальные поддерживаемые валюты имеют два знака. Валюты с тремя minor digits не поддерживаются.
- Доходы/расходы конвертируются на дату операции; капитал переоценивается на каждую дату графика. Будущие оценки не попадают в текущий капитал.
- `reporting_amount_override`, `reporting_currency_override`, `reporting_override_source` сохраняют индивидуальную историческую оценку операции, например из Monefy. Они не меняют исходную сумму и не применяются к переводам.
- Split reports распределяют округление так, чтобы сумма строк совпала с итогом операции.
- Crypto trades сохраняют валюту цены покупки/продажи. Cost basis пересчитывается по историческим курсам покупок; market sync хранит цены в валюте актива. Проценты движения рынка подписаны валютой котировки.

## Курсы и отсутствие данных

`fx_rates` хранит одну каноническую пару/дату, Decimal rate, source и timestamps. Настройки позволяют вручную добавить/изменить курс или импортировать JSON-массив:

```json
[{"base_currency":"EUR","quote_currency":"PLN","rate_date":"2026-09-24","rate":"4.3127","source":"manual"}]
```

API: `GET /api/fx-rates`, `POST /api/fx-rates/bulk`, `GET /api/fx-rates/preflight`.

Поиск курса: дата операции, прямая/обратная пара, затем USD pivot с обеими частями на одну дату; далее предыдущие дни, максимум семь. Будущие курсы не используются. Автоматический внешний поставщик курсов в v1 не подключён.

Недостаток курса возвращает 409 `FX_RATE_MISSING` с парой и датой. Агрегаты показывают ошибку, вместо выдуманного нуля. Native операции и backup доступны независимо от наличия FX. Ответы денежных агрегатов содержат валюту отчёта и использованные даты курсов.

## Миграция и backup

Alembic `f0a100000001` после `d1a6f4c8b729`; backup format 2, чтение v1 и v2. Новый backup включает FX, новые валюты, фактические суммы переводов, overrides и crypto network. Restore валидируется до замены данных и выполняется атомарно.

Старым Goal/Budget/threshold назначается прежняя валюта настроек. Same-currency transfer получает destination_amount из amount. Неизвестная сумма старого cross-currency transfer и неизвестная crypto quote_currency остаются NULL; preflight выдаёт IDs для исправления. Они не угадываются по текущим курсам. Legacy NULL сохраняется при последующем v2 roundtrip. Это может блокировать зависимые расчёты до исправления исходных фактов.

Downgrade с потерей данных не реализован; возврат к старой версии требует соответствующего старого snapshot. Старый пробный Monefy→Aurum импорт нельзя считать корректными исходными единицами без отдельного анализа.

## Проверки

- Backend: полный набор 158 tests passed, включая миграцию, валютную точность, независимые бюджеты и backup.
- Frontend: 59 tests passed; TypeScript и production build прошли, включая Docker build.
- Populated migration проверена в отдельной временной PostgreSQL базе.
- 12 000 синтетических операций, 2921 дата графика: 0,200 s и 8 SQL statements на локальном окружении. Это измерение, не SLA.
- Playwright: все 9 tests passed, включая прежние UI-регрессии и EUR→PLN перевод, оба остатка, ввод FX и смену валюты отчётов с сохранением native остатков. Скриншот настроек проверен визуально.
- Все данные тестов синтетические. Исходный Docker project `aurum` и его пользовательская БД не переустанавливались. Backend tests выполнялись из `/tmp/aurum-multicurrency` против `aurum_test`; UI — отдельный Docker project `aurum-fx-e2e`, порт 3101.
- Известное предупреждение сборщика: основной frontend chunk больше 500 kB; сборку не блокирует.
