# Задание 10: фактическая сумма регулярного расхода

Статус: готово к передаче Claude Code. Источник: [общий план](../project-roadmap.md), подготовка к расходам имущества. Выполнять после принятого PR #49 от актуальной personal.

## Результат

Пользователь подтверждает очередную коммуналку в «Регулярных платежах»: открывает небольшое окно оплаты, вводит фактическую сумму, выбирает счёт и подтверждает. Создаётся один обычный расход сегодняшней серверной датой. Шаблон и его сумма не меняются. Никакого автоматического списания, отдельного журнала коммуналки или повторного внесения той же оплаты.

## Текущий код

- RecurringPost в backend/app/schemas/recurring.py принимает только destination_amount.
- post_recurring в backend/app/services/recurring_service.py блокирует шаблон, проверяет срок/активность/last_posted_date и создаёт Transaction через validate_transaction.
- RecurringPage вызывает usePostRecurring; доход/расход сейчас проводится сразу, перевод между валютами запрашивает destination_amount.
- Использовать существующие модальные компоненты, API и денежную валидацию. Сначала изучить актуальный код, не обходить проверку счетов и категории.

## Контракт и границы

1. Только для расходного шаблона разрешить опциональные amount и account_id при POST /recurring/{id}/post. Старый запрос без них сохраняет прежнюю сумму и счёт. Явные null, ноль/отрицательная/неконечная/слишком точная/слишком большая сумма и несуществующий/недоступный счёт дают понятную 4xx, без записей и продвижения расписания. Формат/пределы суммы согласовать с обычным Transaction, не округлять молча ввод.
2. Сумма относится к валюте фактически выбранного счёта. В окне всегда видна валюта. При смене на счёт другой валюты очистить сумму и потребовать новый явный ввод: не пересчитать справочным FX и не списать прежнее число под новым знаком. Без amount account_id можно переопределять лишь в той же валюте; запрос смены валюты без суммы отклонять.
3. Расходный шаблон: окно с суммой из шаблона как редактируемым значением/ориентиром, счёт из шаблона выбран по умолчанию, отмена без записи. Категория, описание и прочие поля наследуются; отдельную настройку категории здесь не добавлять. Шаблонные account_id/amount не перезаписывать фактическими. Сохраняется нынешняя логика дат и следующего срока.
4. Доходы и переводы остаются с прежним поведением, включая две реальные суммы межвалютного перевода. Новые overrides для них явно отклонять, а не игнорировать. Не менять глобальные курсы/исторические суммы/дату оплаты в этом PR.
5. Атомарность: создание расхода и обновление last_posted_date в одной транзакции. Сохранить блокировку и 409 для повторной/конкурирующей отправки, не допускать двойного расхода. Кнопка подтверждения блокируется при запросе; ошибка оставляет ввод для исправления/повтора. После потерянного ответа повтор не создаёт дубль: актуализировать состояние при 409 и понятно сообщить пользователю результат.
6. После оплаты обновляются счёт, операции, регулярные платежи и все производные финансовые разделы через существующую инвалидацию. В каждом отчёте ровно один расход фактической суммы, без отдельного эффекта от шаблона.
7. Русский/английский, клавиатура, фокус в окне, экран 375px без переполнения. Не использовать window.prompt для нового расходного потока.

## Не включать

Связь с квартирой, массовую разметку истории, личные шаблоны/счета, долги, автосписание, backdated оплаты, выбор другой категории и историю сумм шаблона. Последняя реальная сумма как подсказка — следующий этап: сейчас нет явной связи Transaction↔Recurring, угадывать по одинаковому описанию нельзя. Для этого ограниченного изменения схемы хранения/backup менять не требуется; если обнаружится необходимость — обосновать её до расширения задачи.

## Приёмка

- Backend: старый POST без тела/overrides; расход 100→123.45 с неизменным шаблоном; другой счёт той же валюты; другая валюта с явной суммой и отказ без неё; неверные суммы/счета; запрещённые overrides дохода/перевода; ошибка не продвигает срок; два конкурентных POST создают ровно одну Transaction и одно изменение остатка. Не имитировать конкуренцию двумя последовательными запросами.
- Проверить реальное изменение баланса и суммы в доходах/расходах, включая другую валюту отображения с синтетическим FX. Шаблон не учитывается как вторая операция. После неудачной валидации повтор с корректными данными работает.
- Frontend: отмена; ошибка и сохранение ввода; смена валюты очищает сумму; pending не даёт повторной отправки; 409 обновляет состояние. Компонентные тесты проверяют наблюдаемое поведение.
- Playwright на отдельной синтетической базе: открыть расходный шаблон, сменить сумму/счёт, подтвердить и проверить операцию/баланс/неизменный шаблон; отмена; 375px и клавиатура; существующий межвалютный перевод не регрессирует.
- Запустить backend pytest, frontend build/Vitest и полный изолированный E2E. Не маскировать падения ослаблением проверок; приложить причину и trace для неустранённой нестабильности. Если схема не менялась, старый формат backup остаётся прежним.
