# Задание 16: ремонт override отчётной суммы старого переноса Monefy

Статус: в работе (репетиция на одноразовом Docker-стенде, без production).
Источник: приватный read-only аудит `reporting_amount_override`, найденный
доказанный дефект — не в коде Aurum.

## Контекст (обезличенный)

Прошлый одноразовый перенос Monefy → Aurum (`backend/scripts/monefy_import.py`)
был проверен построчно провенансом (`Monefy SHA256 …; CSV row(s) N` в
`notes` каждой перенесённой транзакции/adjustment). **Импорт оказался
добросовестным**: для каждой живой транзакции с override её native
currency/amount и override currency/amount совпадают с исходным CSV на
100% (проверено сопоставлением по provenance-строке, не по дате/сумме).
Никакой ошибки копирования на стороне Aurum не найдено.

Найденная реальная проблема — в исходных данных Monefy: часть строк CSV
для нескольких счетов (BYN/USD/EUR-native) хранит «converted amount»
**численно равным** native amount, хотя валюты разные. Это математически
невозможно как настоящий исторический курс (BYN/PLN, USD/PLN, EUR/PLN
никогда не были 1.000000 в соответствующий период) и подтверждается чёткой
границей по датам на каждом счёте: до определённой даты 100% кросс-валютных
строк 1:1, после — 0%. Это дефект самого экспорта Monefy (курс не был
настроен для этих счетов в этот период), унаследованный переносом
добросовестно.

## Цель

Убрать доказанно неверный override у затронутых строк (замороженный список
из независимого аудита), чтобы дальнейший отчёт считал сумму через уже
хранимые в БД исторические `fx_rates` (тот же `FXConverter`, тот же
7-дневный previous-rate window, что и для любой другой транзакции без
override) — не изобретая курс.

## Инвариант override-триплета

`reporting_amount_override` / `reporting_currency_override` /
`reporting_override_source` — единая all-or-none тройка
(`money_service.validate_transaction`, обычные write-пути это уже
проверяют). Прямой SQL-ремонт должен повторить этот инвариант вручную:
всегда очищать **все три** поля вместе (в null), никогда частично.

## Что меняем и что нет

Разрешено менять **только** три override-поля, и только в направлении
"старое непустое значение → null" (никогда наоборот, никогда на
вычисленную замену). Явно запрещено трогать: `amount`, `date`, `account_id`,
`category_id`, `description`, `notes`, `tags`, `splits`,
`mandatory_payment_kind`/tax-метаданные, `debt_*`, `expense_asset_id`,
`asset_id`, реальные `transfer`/`destination_amount`, `AssetValuation`,
`fx_rates`, `app_settings`, `updated_at` (по возможности не трогать).

`capital_value` имущества (`routes/assets.py::_to_read`) считается из
ручных `AssetValuation` через `FXConverter`, **не** из связанных расходов
(`expense_asset_id` только группирует расходы для отчётов по стоимости
владения). Оценки квартиры/велосипеда не пересчитываются и не должны
измениться от этого ремонта; только агрегаты связанных расходов в
отчётной валюте.

Источник `manual` и любые корректные (не-1:1) `monefy`-overrides не
трогаем вообще — разница валют сама по себе не ошибка.

## Инструмент

Одноразовый backend CLI (аналог `backend/scripts/monefy_import.py` по духу:
читает приватный frozen preview + CSV, ничего не решает сам). Работает в
одной БД-транзакции:

1. Принимает приватный `--preview` (JSON со списком записей, каждая —
   `transaction_id`, `csv_source_row`, `source_csv_sha256`, `identity`
   snapshot — `account_id`/`type`/`date`/`category_id`/`native_amount`/
   `native_currency` — и `current`/`proposed` для трёх override-полей),
   обязательный `--source-sha256` (внешний, должен совпасть с
   `source_csv_sha256` каждой записи — иначе preview от другого экспорта
   не применится) и опциональный `--journal` путь (приватный, вне Git).
2. Парсер preview (`load_preview`) строго валидирует форму до любого
   обращения к БД: `transaction_id`/`csv_source_row` — позитивные `int`
   (не `bool`), суммы — конечные положительные `Decimal` в пределах
   ledger-точности (`app.core.money.validate_ledger_money`), валюты — из
   поддерживаемого списка ISO-кодов, `current`/`proposed` — ровно три
   ожидаемых ключа (не больше, не меньше), `proposed` — строго все три
   `null`. Дублирующийся `transaction_id` — ошибка всего preview.
   **Математическое доказательство identity** проверяется тут же:
   `native_amount == current.reporting_amount_override` и
   `native_currency != current.reporting_currency_override` — запись, не
   удовлетворяющая этому (обычный корректный override, same-currency
   override, `manual` source), отклоняется как вне scope.
3. `SELECT … FOR UPDATE` по точному списку ID **и** по всем счетам, на
   которые они ссылаются (валюта счёта — часть замороженного identity).
4. Для каждой строки под тем же локом проверяет **все** предусловия перед
   любой записью: тип строго `income`/`expense`; `account_id`, `date`,
   `category_id`, текущая валюта счёта и текущий native `amount` строки
   совпадают с замороженным identity из preview (иначе конкурентное
   изменение после заморозки — конфликт, независимо от override); текущие
   значения трёх override-полей в БД совпадают побайтово с `current` из
   preview; `reporting_override_source` в БД == `monefy`. Любое
   несовпадение — ошибка всей пачки, откат, без частичного commit. Ветка
   "уже применено" (override уже `null`) **тоже** обязана пройти все
   identity-guards — иначе тихий no-op мог бы замаскировать то, что
   транзакция с тех пор изменилась.
5. При успехе всех предусловий — один `UPDATE` по всем ID, три поля → null.
6. По умолчанию dry-run (только отчёт о том, что было бы изменено); реальная
   запись только с `--apply` **и** явной строкой подтверждения на STDIN.
7. Идемпотентность: повторный прогон с тем же preview на уже
   отремонтированных строках не создаёт новых изменений (predicate
   "текущее значение == old" уже не выполняется, но identity всё равно
   перепроверяется → 0 новых записей, не ошибка).
8. Журнал — приватный файл 0600, одна строка = один `os.write()` (не
   несколько вызовов), чтобы частичная запись была невозможна на уровне
   ОС; отсутствие/потеря журнала не единственная защита — повторный запуск
   того же preview самостоятельно доказывает identity/provenance перед
   любой записью, а не полагается на журнал как источник истины.
9. Никакого сетевого доступа, никакого чтения `.env` за пределами
   существующего helper-паттерна, никакого изменения схемы/backup version/UI.

Приватный **operator wrapper** для применения к `aurum-personal` — отдельный
скрипт вне Git (как текущие `task*/_aurum_api.py`), который: берёт свежий
backup **перед** запуском, сверяет SHA256 источника и старые значения по
frozen preview, пишет journal, делает `before`/`after` export и сравнивает
**только** три разрешённых поля (без общего backup-импорта в production).
Это отдельный шаг после приёмки CLI, не часть этого PR.

## Обоснование scope для мелких сумм (native ≤ 1 единица)

212 из 3594 кандидатов имеют native amount ≤ 1 (BYN/USD) — для таких мелких
сумм теоретически можно предположить, что равенство native/converted —
случайное совпадение округления, а не признак дефекта. Проверено явно:
каждая из этих 212 записей (a) находится внутри уже доказанного по крупным
операциям того же счёта окна "100% строк 1:1" (не изолированная аномалия) и
(b) после пересчёта через существующий исторический reference FX даёт
**численно другую** сумму (округление до 2 знаков), т.е. исправление не
no-op ни в одном случае. BYN/PLN и USD/PLN не приближались к курсу 1.0 в
этот период ни при каком округлении до 6 ledger-разрядов, так что случайное
совпадение исключено математически, а не предположением об «actual paid
rate» — курс для отчёта не изобретается, берётся из уже сохранённых
`fx_rates`.

## Репетиция на полном замороженном наборе (не production)

Приватная одноразовая копия свежего production-экспорта (`GET
/backup/export` с продакшена, read-only) была загружена в уникальный
disposable Docker-стенд (случайный порт, не 3003/3101, отдельное имя
compose-проекта), затем весь набор из 3594 записей применён guarded CLI
(`--apply`, одна атомарная транзакция). Полный diff backup-экспорта
до/после подтвердил: изменились ровно 3594 транзакции, и для каждой —
**только** три override-поля; счета (native balance), assets (включая
`capital_value`, который считается из ручных `AssetValuation` через
`FXConverter`, а не из связанных расходов), `asset_valuations`, `fx_rates`
и `app_settings` побайтово идентичны. Исправленный backup сам проходит
export→import→export без дрейфа. Повторный прогон того же preview —
0 новых изменений, 3594 already_applied, 0 конфликтов (идемпотентность).
Отчёты `/cash-flow` и `/net-worth/summary` в PLN/USD/EUR пересчитаны тем
же `FXConverter` без сетевых FX-запросов; приватные числовые дельты — вне
Git, в `/private/tmp/bridge/monefy-rehearsal/` и
`/private/tmp/bridge/monefy-override-audit/` (0700/0600), с production
никогда не смешивались (копия импортирована только в disposable стенд,
production не менялся).

## Не входит / открытый вопрос

Две строки исходного CSV (одинаковая валюта PLN/PLN, без description,
недалеко от даты экспорта) не имеют вообще никакого живого счётчика в базе
— ни транзакции, ни adjustment. Их provenance полностью отсутствует в
`notes` всех живых транзакций. ID соседних живых транзакций образуют ровно
такой же разрыв (пропущены именно те два id, что соответствуют этим CSV
строкам по порядку), что указывает на обычное удаление уже существовавших
записей (например, дубликат/ошибочная ручная запись, убранная пользователем
после переноса), а не на дефект самого скрипта переноса (который
детерминированно и проверяемо сохраняет каждую строку 1:1). Восстанавливать
эти две операции или объявлять их «потерянными» без дополнительного
изучения пользователем — вне рамок этого задания; оставляем отдельным
пунктом, не исправляем.

## Критерии приёмки

- Синтетические тесты нового CLI (не затрагивают `aurum-personal`,
  порт 3003, и не production-порт 3101): malformed/duplicate/неоднозначный
  preview отвергается; конфликтующая живая строка (текущее значение !=
  `current` в preview) откатывает **всю** пачку; transfer/adjustment/
  debt_in/debt_out/`manual`-source исключены предикатом; корректные
  (не-1:1) overrides не входят в preview и не трогаются; roundtrip трёх
  null через backup export/restore не теряет и не искажает данные; после
  ремонта отчётная сумма берётся из уже существующих `fx_rates` без новых
  курсов (FX coverage проверяется, а не изобретается).
- Репетиция на одноразовом Docker-стенде (случайный порт, не 3003/3101,
  уникальное имя проекта): либо целиком синтетические данные для проверки
  атомарности/инвариантов, либо (допустимо) приватная копия реального
  экспорта — вне Git, только локально, только для сверки точного
  замороженного набора изменений и отчётов (dashboard cash flow, стоимость
  владения имуществом в PLN/USD/EUR тем же `FXConverter`) до/после; реальные
  переводы, мультивалютный капитал и `AssetValuation` не меняются — сверяется
  явно.
- Только новые/затронутые backend-тесты локально один раз; полный
  backend/frontend/E2E не повторяется.
- До готовности репетиции — никаких production-записей, коммитов в
  `personal`, merge или deploy. PR открывает и мержит только Codex после
  зелёного CI.
