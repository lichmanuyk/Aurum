# Работа над персональным форком

`docs/project-roadmap.md` — общий план и статус. `docs/tasks/` — отдельные
задания с критериями приёмки. Codex ведёт план, готовит задания и теперь сам
запускает исполнителя (Claude Code через CLI) в изолированной ветке от
актуальной `personal`: пользователь больше не передаёт промпты и ссылки на PR
вручную между Codex и исполнителем — Codex сам получает результат, при
необходимости выдаёт исполнителю следующий ограниченный промпт на исправления
в той же ветке и сам открывает PR в `personal` через GitHub MCP. Пользователь
принимает решения, для которых нужны его личные данные/предпочтения, и явно
разрешает слияние и развёртывание.

## Один цикл

1. Codex выбирает следующий ограниченный пункт плана, проверяет текущий код,
   записывает цель, границы, инварианты и критерии приёмки в `docs/tasks/`.
2. Codex запускает исполнителя в отдельной ветке от актуальной `personal`:
   реализация ограничена этим пунктом, проверяется на синтетических данных,
   запускаются нужные серверные, клиентские и браузерные тесты.
3. Codex сам получает от исполнителя итог (список изменений, фактические
   результаты проверок, оставшиеся ограничения) и сверяет его с заданием —
   смотрит diff и результаты тестов, при необходимости выдаёт новый
   ограниченный промпт на исправления в той же ветке. Задача не считается
   закрытой, если тесты или обязательные CI-проверки не прошли.
4. После проверки результата Codex открывает PR в `personal` через GitHub MCP,
   чтобы запустить CI. Слияние выполняется только после зелёных обязательных
   проверок на последнем коммите; затем обновляется статус плана.
5. Если пользователь уже разрешил слияние и развёртывание задачи, Codex
   доводит их до конца без повторного запроса разрешения: копия перед деплоем,
   проверка запуска и сохранности финансовых данных после него обязательны.
   Новое применение к личным данным требует согласованного набора изменений.

Если изменение требует настоящих финансовых данных, сначала реализуется и
проверяется универсальный механизм на синтетических примерах. Применение к
личным данным (конкретное имущество, разметка истории и т.п.) — отдельный,
явно согласованный шаг после приёмки механизма; перед ним обязательны
резервная копия и сверка после. Ни агент, ни тесты не должны использовать
личную базу `aurum-personal` как тестовую.

## Правила для задания и PR

- Сохранять `main` для upstream; рабочая схема — отдельная ветка → PR →
  `personal`. Не коммитить в `personal` напрямую и не смешивать независимые
  пункты в одном PR.
- В задании формулировать наблюдаемое поведение и запреты на нарушение
  финансовой математики; способ реализации агент выбирает после чтения кода.
- Не менять реальные счета, операции, настройки, ключи, бэкапы и Docker в
  ходе реализации. Продакшен на порту 3003 — не тестовый стенд.
- Проверять совместимость старых резервных копий при изменении схемы данных.
  Добавлять миграцию, тест восстановления и обновлять версию формата только
  если изменение действительно требует этого.
- Сначала закончить реализацию и ревью логики, затем локально запускать новые и затронутые тесты. Полный набор выполнять в финальном GitHub CI, не дублировать его локально и не повторять весь E2E ради стабильности без конкретной причины. После исправлений повторять затронутые проверки; обязательный CI на последнем коммите, проверку запуска и данных после деплоя сохранять.
- UI проверять браузерным сценарием на отдельном стеке, включая узкий экран.
  Новые тексты поддерживать на русском и английском. В PR перечислять
  команды и фактические результаты проверок; ждать зелёный CI.
- Не удалять существующие комментарии без замены актуальными. Не включать в
  diff личные данные, секреты или скриншоты с ними.

Задание считается закрытым после проверки Codex и фиксации результата в
плане. Самоотчёт исполнителя — вход для проверки, а не доказательство её
успеха.

После приёмки функционального PR Codex обновляет docs/release-notes.md: 1–2 предложения о поведении и где попробовать. Слияние и проверенное развёртывание отмечаются отдельно.
